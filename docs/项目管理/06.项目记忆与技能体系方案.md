## 一、结论

**要搭，但只搭「够用」的轻量版**：约 4 个文档 + 3 个先建的技能，半天内能落地。

理由：

1. Plane 的工作天然跨会话、跨 AI（Plane助理、zcode、将来的 codex/Orca 角色），现在每次都靠我口头交接，zcode 也读不到明哥今天定的那些规矩（比如「调研阶段 main 直推」「测试口令可明文」）。
2. 有两处文档已经过时、互相冲突：mini 仓库的 `00.项目章程.md` 还写着「不 commit / push」；ThinkYM 的 plane README 还写着「凭据一律不入库」「调研文档尚未提交」。没有统一入口，这种冲突会越积越多。
3. 一旦进入开发阶段（改核心文件 + 同步上游），没有规则就会出现合并冲突、决策丢失、AI 各干各的。

**不搭的**：不做团队协作那套（成员表、权限流转、逐步授权）、不做 Jira/索引站那类发布登记、不建一堆角色。Plane 是明哥一人负责全程，规则的目标只有一个：**让任何一个 AI 开工 5 分钟内恢复上下文，并且不用再问明哥已经定过的事。**

## 三、借鉴 vs 不采用

### 借鉴

| 借鉴点                                                           | 为什么                                                             |
| ---------------------------------------------------------------- | ------------------------------------------------------------------ |
| 项目记忆放仓库内、技能放仓库内 `.claude/skills/<name>/SKILL.md`  | zcode / Claude Code / codex 在仓库里就能读到，不依赖 Grok Bot 环境 |
| 角色档案的四要素：**启动偏好、职责、边界、交付**                 | 简单有效，换 AI 或模型时只改一处                                   |
| 把信息分成「已确认 / 建议 / 待确认」，待确认的不许自行固化       | 防止 AI 把讨论当决策，尤其 M2 探索期想法多                         |
| 委派任务书模板（目标、依据、允许改的文件、禁止事项、验收与证据） | zcode 批次提示词已经是这个思路，固化成模板即可                     |
| 复核实际产物，不凭 AI 自报判通过                                 | 调研批次验收、开发验收都用                                         |
| ThinkYM 的真相源原则：一个事实一个家，其余只放链接               | 解决「两处重复」                                                   |

### 不采用

| 不采用                                                    | 原因                                                                                        |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 一份 200KB 的单体 CLAUDE.md，决策条目写成长段             | 每次开工都要吞下整份，成本高；Plane 记忆文件限 ≤150 行，细节放 ADR 文件，记忆里只放一行索引 |
| 六阶段 + 每个节点单独授权（提交、登记、合并 main 分别问） | 那是为公司流程和同事协作设计的；明哥对 Plane 全程负责，已授权的范围内 AI 直接做，事后汇报   |
| Jira AUT、索引页、构建站、更新说明、版本号体系            | 公司交付登记需要；Plane 的任务看板用 Linear，文档不需要版本号体系，git 历史即版本           |
| 「基线 + 迭代」文档模型                                   | 适合持续变化的 PRD；Plane 的权威是代码 + 上游，文档以调研、ADR、技术方案为主                |
| 双份维护技能（Grok 版 + 仓库版）                          | 维护成本高、易不一致；Plane 只在仓库里放一份，Plane助理直接读仓库                           |
| 7 个角色、成员/干系人表、权限流转                         | 一人项目，最少角色即可（见第六节）                                                          |
| ThinkYM 的「凭据永不入库」原样照搬                        | 明哥已决定：Plane 仓库里的**测试口令可明文**；正式凭据仍只在 Vault（见第五节）              |

## 五、规则（写入 `工作约定.md`）

**1. git**

- `origin` = 明哥 fork（公开）；`upstream` = makeplane/plane。
- **调研阶段**：直接在 `main` 上提交并及时推送（已授权）。**开发阶段**：按 Linear 任务开分支 `feat/<YUE-编号>-简述`，完成并验证后合回 `main`（授权方式见问题 3）。
- `preview` 只用来同步上游，**任何情况下不在 preview 上改**。默认**不向上游提 PR**（上游 AGENTS 里「PR 开到 preview」的规则对我们不适用）。
- 提交前：先 `git status` 确认分支和与 origin 同步；只 `git add` 本次路径，不 `git add -A`；不 force push、不改写已推送历史；冲突即停并汇报。
- 仓库有 husky + lint-staged（oxfmt 会自动改格式），**不用 `--no-verify`**。
- **同步上游（建议）**：每月一次 + 出重要 release 时即时看一眼。流程：`git fetch upstream` → `preview` 快进到 `upstream/preview` 并推送 → 新建 `sync/YYYYMMDD` 分支把 `preview` **merge** 进来（不 rebase，因为 main 已公开）→ 解决冲突、跑 `pnpm check` 与冒烟 → 合回 `main`。改核心文件前，先在「上游冲突热点」清单（调研 R5 的产出）登记，尽量用新增文件/扩展点而不是改上游文件。越早建立节奏越省事，现在 main 上只有文档，同步几乎零成本。

**2. 提交规范**

- 中文，格式 `类型(范围): 摘要`。类型：`docs`、`feat`、`fix`、`refactor`、`test`、`chore`、`sync`（同步上游）。示例：`docs(调研): 第 1 批云端实测补完`。
- 提交人：AI 用 `姜子牙团队 <yueming1985+thinkym-agents@gmail.com>`，明哥自己提交用自己的身份。
- 新增 `.py/.ts/.tsx` 文件按上游 `COPYRIGHT_CHECK.md` 加版权头（许可细则等 R8 许可审计恢复后再定）。

**3. 文档**

- 沿用 zcode 已建的编号目录：`01.追赶正式版/`、`02.产品设计/`、`03.技术方案/`、`04.测试发布/`、`项目管理/`、`运维/`；文件名中文，模块文档用 `对比.md` 这类固定名。
- 每篇文档第一行写状态与日期（如「状态：草稿｜2026-11-14」），事实要分「已确认 / 推断 / 待确认」。
- 公开仓库只放产品、技术、调研；个人规划、M2 创意细节放 ThinkYM。

**4. 决策记录（ADR）**

- 日志：`02.会议与决策记录.md` 一行一条（日期、决定、依据、是否有 ADR）。
- 重大决策（影响架构、范围、许可、同步策略）才写 `决策/ADR-NNN-标题.md`，**≤30 行**，固定栏目：状态（提议/已定/废止）、背景、决定、备选与放弃原因、后果（含对同步上游的影响）、依据链接。
- 明哥在对话里拍板的事，当天写入日志，并更新 `项目记忆.md` 的决策索引。

**5. 凭据**

- 测试账号口令可明文，只放 `docs/运维/测试账号.md`，因为仓库公开，**只限测试账号、可随时作废**。
- 正式凭据（LLM key、生产账号、正式环境口令、云端付费账号）只在 Vault，文档里写「存于 Vault：条目名」。
- `.env`、`vite.config.local.ts`、`.logs` 等本地文件不进 git。

**6. 何时必须问明哥**（其余 AI 自行决定，事后汇报）

- 产品方向、范围取舍、里程碑优先级的变化。
- 花钱、额度策略变化（套餐、新订阅）。
- 对外公开或发布（公开部署、对外提供服务、发文章/开源动作）。
- 不可逆操作：force push、删分支、重置数据库、删除云端测试数据以外的账号内容。
- 许可与合规边界（R8 恢复后）、同步上游策略的变更、本规则本身的变更。

## 六、角色与分工

明哥是产品、设计、开发、测试、部署、运营的唯一负责人和最终决策者。AI 角色**最少 3 个**，其余用到再加：

| 角色             | 谁                                                              | 职责                                                                                                   | 边界                                                           | 启动偏好                           |
| ---------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- | ---------------------------------- |
| 负责人           | 明哥                                                            | 决策、验收、定方向                                                                                     | —                                                              | —                                  |
| **统筹**         | Plane助理（Grok Bot）                                           | 恢复上下文、拆批次/任务、写任务书、复核产物、提交推送、维护 STATUS/Linear/记忆、向明哥汇报并提拍板问题 | 不替明哥做第六节列出的决策；不自己大量写业务代码（重活派出去） | Grok Bot                           |
| **执行**         | zcode（mini，GLM start plan）                                   | 调研批次、云端实测、文档撰写，开发阶段承担主要编码                                                     | 只做任务书允许的文件；产出必须带证据；不自行扩范围             | zcode · glm-5.3 · high（沿用现有） |
| **评审**（按需） | 复用 ThinkYM 的评审员/技术专家路由 R4（codex gpt-6.1-sol high） | 架构、方案 red-team、核心改动的独立评审                                                                | 只出评审意见，不改代码                                         | 见 `任务路由约定.md`               |

开发阶段才考虑再加「测试」（浏览器冒烟/回归，可用 zcode 另开会话扮演）。**不建**产品专家、前端、后端等多角色，Plane 的前后端不分工，由「执行」按任务书完成。

加载规则（借鉴 Autovado）：主 AI 开工读 L0 → L1 项目记忆 → 自身角色；worker 只读任务书指定的资料，不假设有会话记忆。

## 九、需要明哥拍板的问题

1. 体系规模怎么定？
   A. 轻量版（本方案：4 个文档 + 3 个 P0 技能，开发前再补 P1）——推荐
   B. 极简版（只加 `CLAUDE.md` 和 `项目记忆.md`，技能等开发开始再建）
   C. 接近 Autovado 完整版（多角色、六阶段流程、双份技能）

2. 入口文件怎么放？上游自带的 `AGENTS.md` 是 codex 等工具会读的。
   A. 在 `AGENTS.md` 末尾追加一个固定小节（约 10 行），再新增 `CLAUDE.md`——推荐；同步上游时若冲突，保留双方即可
   B. 不动 `AGENTS.md`，只新增 `CLAUDE.md`；codex 等工具读不到，靠任务书里写明「先读 CLAUDE.md」，同步上游零冲突

3. 开发阶段，功能分支合回 `main` 的授权？
   A. 验证通过（`pnpm check` + 冒烟）后 AI 自行合并，事后汇报——推荐，符合 OPC 节奏
   B. 每次合并前都要明哥点头
   C. 小改动自行合并；涉及上游核心文件、数据库迁移、依赖升级的要明哥点头

4. 同步上游的节奏？
   A. 每月一次，加重要 release 即时看——推荐
   B. 每个上游正式 release 同步一次
   C. M1 阶段性完成前暂不同步，只登记差距（风险：改动越多，后面冲突越重）

5. 公开仓库里放什么？fork 是公开的，docs 里已有测试口令和云端页面快照。
   A. 仓内只放产品/技术/调研（含测试口令），个人规划、M2 创意、真实凭据留 ThinkYM 和 Vault——推荐
   B. 不限制，什么都可以放仓内
   C. 另建私有仓库放文档，公开 fork 只放代码（会拆开文档与代码，且失去 fork 关系的便利，需另评估）
