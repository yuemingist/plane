## 为什么不能硬合（技术前提）

官方换的是整套 Propel 设计系统，再加上 React 与路由大版本。我们 Step01 / Step02 的前端是在旧体系上改的，硬合很容易看起来合并成功，界面却大面积错位。

盘点时把自有改动分成三类：

- **A. 后端 / API**：工作流壳、自定义属性、流转规则、按类型可用状态、时间跟踪开关等。大概率可合并或 rebase，但也要检查官方是否新增了同号迁移（我们已有 0126–0129，若官方也占用这些编号，必须先解决冲突，不得覆盖官方迁移，也不得丢掉我们的迁移）。
- **B. 机械前端**：文案、开关接线、API 调用、不依赖旧设计系统的薄封装。由你实现，技术专家抽查。
- **C. 设计系统相关 UI**：类型设置、属性表单、筛选面板、类型芯片、工作流设置页等。必须按 Propel 新组件重做，而不是死磕冲突。这是专家审核的重点。

### 派单与取回输出


推理档必须是中等。升级后若帮助信息显示 pi 用 `--thinking medium` 而不是 `--effort medium`，以实际能选中「中等推理」且回执可核对的参数为准，并写进断点记录。`--model` 需带 `openai-codex/` 前缀。
