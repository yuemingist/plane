## 1. 结论速览

- **根因（一句话）**：React StrictMode（开发态）把挂载 effect 按「setup → cleanup → setup」双执行，`WorkItemFiltersHOC` 的卸载清理 effect 在模拟卸载阶段把 render 期注册进 `WorkItemFilterStore` 的 filter 实例 `deleteFilter` 删掉，而 `useMemo` 不会重建——store 里实例永远缺失，页头 `WorkItemFiltersToggle` 读 `getFilter()` 得 `undefined`，点击即报 `Filters toggle error - filter instance not available`（filters-toggle.tsx:38），面板无法打开。

## 3. 调用链与根因

### 3.1 谁创建 filter 实例、何时注册

```
IssuesHeader（页头，与页面 body 平行渲染）
└─ HeaderFilters（components/issues/filters.tsx:142）
   └─ WorkItemFiltersToggle（components/work-item-filters/filters-toggle.tsx）
      └─ getFilter(entityType, entityId)  ← 读 store，实例不存在 → filters-toggle.tsx:38 console.error

ProjectLayoutRoot（页面 body，components/issues/issue-layouts/roots/project-layout-root.tsx）
├─ useSWR → issuesFilter.fetchFilters()（未返回前 return <></>，HOC 不挂载）
└─ fetch 完成后挂载 ProjectLevelWorkItemFiltersHOC → WorkItemFiltersHOC
   └─ WorkItemFilterRoot（filters-hoc/base.tsx）
      ├─ 【旧】render 期 useMemo → store.getOrCreateFilter()  ← 此处注册实例
      ├─ 【旧】useEffect(() => () => deleteFilter(...))       ← 卸载清理
      └─ children({ filter }) → WorkItemFiltersRow / 各布局
```

### 3.2 根因机制（StrictMode 双效应）

`apps/web/app/entry.client.tsx:45` 以 `<StrictMode>` 包裹 `<HydratedRouter>`。React 18/19 开发态对每个组件的挂载 effect 执行 **setup → cleanup → setup** 三部曲。于是 `WorkItemFilterRoot` 挂载时：

1. render：`useMemo` 调 `getOrCreateFilter` → 实例 A 注册进 store（key=`PROJECT-{projectId}`）；
2. effect setup（第一次）：无操作；
3. StrictMode 模拟卸载 → **cleanup 执行 `deleteFilter` → 实例 A 从 store 删除**；
4. effect setup（第二次）：无操作——`useMemo` 不重跑，**没有任何代码重新注册**。

终态：页面 body 持有实例 A 的过期引用照常渲染（列表/筛选行功能看似正常），但 store 里 `getFilter(PROJECT, projectId)` 永远 `undefined` → 页头 toggle 点击即命中 `filters-toggle.tsx:38` 的 guard。这也是「列表显示正常、唯独筛选打不开」的原因。生产构建不含 StrictMode 双效应，故该缺陷只在 dev server（本 mini 环境的部署形态）暴露。

### 3.3 为何 Step01 期间才被发现

- 缺陷随上游 #7810「work item filters revamp」（filters HOC + store 注册/清理架构引入）即存在，非 Step01 引入（§2.2 实证）。
- Step01 之前筛选类用例未被执行到该路径；Step01 首次把「筛选面板打开 → 用 Type/Parent type」写进 TC-1B-006/007，第一次点击真实触雷。
- 本机部署形态是 `react-router dev`（开发构建，StrictMode 生效），云端 Business 是生产构建——同源代码两边表现不同，导致调研期对齐云端行为时未暴露。

### 3.4 连带缺陷（复验中发现并同批修复）

**配置反应性缺失**：修复面板打开后，Type / Parent type 两个筛选项仍不在菜单。定位：`apps/web/hooks/work-item-filters/use-work-item-filters-config.tsx` 的 `projectIssueTypes` 用 `useMemo(() => getTypesByProjectId(projectId) ?? [], [getTypesByProjectId, projectId])`——依赖是稳定引用，memo 一次计算后**永不重算**：首次渲染（类型未取回）得 `[]`，类型 API 返回后组件虽因 MobX 追踪重渲染，但 memo 依赖未变 → `type_id`/`parent__type_id` 配置永远 `isEnabled=false` → 菜单缺项。该缺陷被 BUG-08 阻塞掩盖（TC-1B-006 从未能打开菜单检查），属 Step01 1b-4 的潜伏缺陷，随本次一并修复（见 §4-F2）。

**后端 `parent__type_id__in` 缺失**：修复菜单后，UI 选 Parent type 触发 `?filters={"parent__type_id__in":"<uuid>"}` → API 400 → 列表被清空。API 探针对照：`type_id`/`type_id__in`/`parent__type_id` 均 200，唯 `parent__type_id__in` 400——Step01 BE-3 只声明了单值形态，而前端 rich filters 的多选条件统一发 `<key>__in` 后缀。随本次补齐（见 §4-F3）。

## 4. 修复内容（最小改动，无新增依赖、无既有 API 变更）

### F1 实例生命周期改由 effect 持有（根因修复）

`apps/web/components/work-item-filters/filters-hoc/base.tsx`：

- 实例注册从 render 期 `useMemo` 移入挂载 effect（entity 作用域 deps）：setup `getOrCreateFilter` → cleanup `deleteFilter`。StrictMode 的 cleanup→setup 序列自动完成「删了再重建」，store 与渲染树终态一致；
- 选项同步拆为第二个 effect（镜像 store 对既有实例的更新路径：`updateExpressionOptions` + `onExpressionChange`），保留旧代码「依赖变更不重建实例」的语义，避免表达式/可见性状态被重置；
- children 改读 `getFilter()`（store 为唯一事实源，observer 随实例增删重渲染）；children 类型放宽为 `IWorkItemFilterInstance | undefined`（与外层 `TSharedWorkItemFiltersHOCProps` 原有类型一致——外层本就传 `{ filter: undefined }`）；全部消费方原本就有 `filter && <WorkItemFiltersRow/>` 守卫，逐一核对无裸用。

### F2 类型筛选配置反应性（连带缺陷 1）

`apps/web/hooks/work-item-filters/use-work-item-filters-config.tsx`：`projectIssueTypes` 的 memo 依赖补入反应式取数标志 `areTypesFetched(projectId)`（computedFn 读 `fetchedMap` observable，render 期被 observer 追踪），类型列表到达后 memo 重算 → `type_id`/`parent__type_id` 配置置 enabled → 菜单出现两项。不改任何配置工厂签名。

### F3 后端补 `parent__type_id__in`（连带缺陷 2）

`apps/api/plane/utils/filters/filterset.py`：按相邻 `type_id__in` 同款声明补一行 `parent__type_id__in = UUIDInFilter(field_name="parent__type_id", lookup_expr="in")`，并补 pytest 断言（filterset 直查 + 多值）。0 迁移、0 依赖变更。
