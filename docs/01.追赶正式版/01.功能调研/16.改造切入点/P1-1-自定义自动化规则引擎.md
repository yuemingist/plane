## 1. 目标与云端形态

在 CE 项目设置中从零补齐「自定义自动化」规则引擎，对齐云端 Business 形态（58 号实测）：

- **入口**：项目设置 → 自动化页新增「自定义自动化」区（表格 10 列：标题/最后运行时间/创建时间/最后更新时间/最后运行状态/平均持续时间/所有者/执行次数/状态/行操作）+「创建自动化」按钮；创建弹窗仅 名称\*+描述。
- **构建器**（`/settings/projects/{id}/automations/{ruleId}/`）：三栏布局=左侧设置导航+中间画布（触发器⚡「如果」→操作「那么」卡片）+右侧配置面板；顶部面包屑+活动按钮+启用/禁用+更多操作。
- **触发器 5 种**：Work item created / Work item updated / State changed / Assignee changed / Comment created（下拉带「Plane 事件」分组头）。
- **条件 6 字段**：State/Type/Label/Assignees/Created by/Priority × is 运算符（UI 锁定）× 值多选；条件可多个也可不加。
- **操作 5 种**：添加评论/添加链接/更改属性（6 属性 State/Priority/Assignee/Labels/Start Date/Due Date × add/remove）/删除工作项/归档工作项。
- **执行语义**（58 号 D-06/D-07）：异步执行（实测延迟 1-2 分钟）；条件在**事件时刻快照**上评估（完整弹窗带优先级创建才触发 created 规则）；执行者=**Automation Bot** 系统身份写活动流。
- **可观测**：规则列表执行次数/成功失败率徽章/平均持续时间（150-300ms）；活动面板=配置历史+逐工作项运行卡片（时间/耗时/成败）+「显示失败」开关。
- 深测文档：`docs/01.追赶正式版/01.功能调研/58.自动化与工作流深测/对比.md`；规格草案：`18.数据模型与API规格草案/03.重复工作项与自动化.md`。

## 3. 后端改动面（从零建，新增为主）

1. **模型（5 新表，新增迁移）**：`Automation`（name/description/scope/status/is_enabled/is_global/project_ids M2M/bot_user_id FK/current_version_id/run_count/last_run_at）、`AutomationNode`（node_type: trigger|action|condition、handler_name CharField 无 choices、config JSON、next_scheduled_at/last_triggered_at、version_id）、`AutomationEdge`（source/target/execution_order/version_id）、`AutomationActivity`（verb/field/old-new value/actor/automation/node/edge/run 引用）、`AutomationRun`（work_item/status/duration_ms/started_at——云端运行卡片推断表，18 号标低可信度，按 UI 观测字段设计）。均继承 BaseModel/ProjectBaseModel（列结构对齐 00 号总则）。
2. **一期简化**：按 20 号路线图建议先做**线性规则**（trigger→conditions[]→actions[] 单链），表结构仍按 nodes/edges 建以兼容二期画布图结构。
3. **API**：项目级+工作区级两组 ViewSet/视图：automations CRUD、`{id}/status/`（唯一启停通道，删除前须禁用）、nodes/edges 子资源、`{id}/activities/`、runs 列表。挂 `apps/api/plane/app/urls/` 新独立模块（安全修复密度高区，17 号同步策略建议新文件+独立 urls）。
4. **执行引擎**：issue 信号挂接点（post_save/post_delete 或从 `issue_activities_task` 的活动写入点分流）→ `automation_evaluate` Celery 任务（事件 payload 快照评估条件，对齐 D-07 语义）→ 逐节点执行 handler（add_comment/change_property/delete/archive/add_link 5 个 handler 函数）→ 写 AutomationRun/Activity；执行者 bot_user（Automation Bot 建为系统 User，活动流 actor 指向它）。
5. **内置规则收敛**：`Project.archive_in/close_in` 字段保留不动；UI 层后续可把两开关映射为系统 Automation（18 号 §5 迁移兼容条目 3）。

## 8. 上游冲突面（风险：低-中）

- 后端：新增文件+独立 urls 模块，**低**；但 issue 信号挂接若改 `issue_activities_task.py`/`webhook_task.py` 既有活动分发点，该区是安全修复高密度区（17 号 §3）——建议只读消费活动流数据而非改写。**隔离策略**：独立 `plane/bgtasks/automation_task.py` + 独立 urls。
- 前端：项目设置自动化页（`automation-panel.tsx`）需追加区块=**中**（该组件不在 propel 迁移/RR8 高危路径上，但设置页容器可能被动到）；构建器全新目录=低。**隔离策略**：列表区用插槽式追加，构建器独立路由页。
- i18n：`automation.json` 为无消费方官方资产，冲突概率低；注意不重排既有键。
- 官方先做掉风险：17 号判定 Business 功能、90 天零相关提交，短期无交叠。

## 9. 风险与未知

1. `AutomationRun` 表结构为推断（云端运行卡片不可点开），字段面以 UI 观测为准、留扩展列。
2. 触发器 Work item updated / Assignee changed / Comment created 与操作 添加评论/添加链接/删除/归档 的配置面板未逐个实测（58 号待验证 3）——按 handler 语义自设计，云端后续复核。
3. "启用即生效"边界（58 号 SURVEY-1 首次触发丢失样本）：追赶需定义启用瞬间的事件窗口语义。
4. 执行延迟 1-2 分钟是云端表现；CE 单机 Celery 可更快，不刻意对齐。
5. run_script handler（locale 出现但 UI 5 操作未含）是 SDK v2/Enterprise 能力，一期不实现。
6. 时区：调度型触发器（fixed schedule）涉及 `workspace_timezone`（17 号对象 7 迁移名佐证该字段体系存在），一期线性触发器可不涉及，二期做。
