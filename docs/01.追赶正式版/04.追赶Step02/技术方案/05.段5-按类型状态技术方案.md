## 1. 数据模型与迁移

### 1.1 模型选型：项目桥 M2M vs JSON 字段 vs 新建关联表（产品方案 §4 评估）

| 方案                                              | 优点                                                                                                                        | 缺点                                                                                              |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **A. `ProjectIssueType` 加 `states` M2M**（选定） | FK 约束状态引用；查询可 join（下拉过滤/校验一次查询）；blank=True 天然表达「空=继承」；through 表随桥删除级联清理；零新实体 | 新迁移；through 表名由 Django 自动生成                                                            |
| B. 桥加 `state_ids` JSONField                     | 无表变更…实际仍有迁移；单次读写                                                                                             | 无法 DB 级防脏引用；软删状态清理靠应用层（段 3 技术方案 §1.1 已论证 JSON 弱于关系表）；无 FK 级联 |
| C. 新建 `ProjectIssueTypeState` 显式关系表        | 与段 3 `WorkflowTransition` 风格一致；可控唯一约束                                                                          | 与 Django M2M through 表能力完全重合，多写一个 model + serializer 没有额外收益                    |

**结论：选 A**。`M2M(blank=True)` + through 表已提供 FK 完整性、级联与去重，段 3 选显式表是因为需要 `(workflow, from_state, to_state)` 三元业务唯一约束，本段只需要「类型 × 状态」集合语义，M2M 即是。

```python
# plane/db/models/issue_type.py
class ProjectIssueType(ProjectBaseModel):
    ...
    # 段 5：该类型在项目内的可用状态集合；空 = 继承项目全量状态池（产品方案 A2）
    states = models.ManyToManyField(
        "db.State",
        blank=True,
        related_name="project_issue_types",
        verbose_name="Available states",
    )
```

## 2. 后端

### 2.1 读：类型列表/详情透出 `state_ids`

- `WorkItemTypeViewSet._annotated_queryset` 追加 `state_ids` 子查询：对项目桥 `ProjectIssueType` 的 through 表 `ArrayAgg`（join `project_issue_type_states`，过滤 `state.deleted_at` 不可行——ArrayAgg 用子查询实现：`ProjectIssueType.objects.filter(issue_type=OuterRef("pk"), project_id=…, deleted_at__isnull=True).annotate(arr=ArrayAgg("states__id", distinct=True)).values("arr")[:1]`，Coalesce 兜底空数组）。
- `IssueTypeSerializer` 加 `state_ids = serializers.SerializerMethodField()`（读 annotate 注入的实例属性；无值 → `[]` = 继承全量）。`[]` 在前端语义即「未配置」，不区分「配了又全删」（两者等价，产品方案 A2 白名单语义下同一状态）。

### 2.2 写：桥 states 全量替换端点

挂载 `WorkItemTypeViewSet` 新 action（路由 `apps/api/plane/app/urls/issue_type.py` 追加）：

| 方法 | 路径                             | 语义                                                                                                                       | 权限               |
| ---- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| GET  | `…/work-item-types/<pk>/states/` | 该类型可用状态 id 列表（空 = 继承全量，响应体带 `inherits_all: true` 便于前端文案）                                        | ADMIN/MEMBER/GUEST |
| PUT  | `…/work-item-types/<pk>/states/` | **全量替换**：body `{"state_ids": [...]}`；空数组 = 清空 = 恢复继承全量；服务端校验每个 state 属本项目且未软删，非法 → 400 | ADMIN/MEMBER       |

- 实现走 `bridge.states.set(state_ids)`（事务内 diff）；桥不存在时 get_or_create（对齐 `mark_default` 惯例）。
- 不写更改历史（产品方案 §4：WorkflowChangeLog 是工作流域历史，类型域无历史面板）。

### 2.3 校验 helper（与段 3 共存于 `plane/app/views/workflow.py`）

```python
def validate_state_allowed_for_type(project_id, type_id, state_id) -> dict | None:
    """类型可用状态校验（段 5）。返回 None=放行；dict=拒绝（code=issue_type_state_not_allowed，
    含 type_name/state_name）。type_id 为空 / 桥不存在 / 集合为空（继承全量）/ state ∈ 集合 → 放行。"""
```

- 查询：`ProjectIssueType.objects.filter(project_id=…, issue_type_id=type_id, deleted_at__isnull=True)` 取桥；`bridge.states.filter(deleted_at__isnull=True)` 做成员判断（软删陈旧引用被过滤，产品方案 A9）。
- 段 0-4 零回归：`type_id` 为空或桥集合为空时仅 1-2 次轻量查询即返回；行为与今天一致。

### 2.4 三处校验挂载（`plane/app/views/issue/base.py`，与段 3 顺序）

1. **改状态**（`partial_update`，请求含 `state_id/state` 且 ≠ 当前）：在段 3 `validate_state_transition` **之前**调用 `validate_state_allowed_for_type(project_id, issue.type_id, requested_state_id)`（用工作项**当前类型**）。串联顺序：**先可用集合后流转规则**（产品方案 A3），两个 400 code 区分：`issue_type_state_not_allowed` → `workflow_transition_not_allowed`。被拒不进 `serializer.save`、不触发 issue_activity（段 3 既有模式）。
2. **切换类型**（`partial_update`，请求含 `type_id/type` 且 ≠ `issue.type_id`）：
   - 请求同时改 state：用**新类型 + 新 state** 校验集合（一次校验覆盖），随后按（1）对 state 做流转校验（源状态 = `issue.state_id`，段 3 规则类型无关，保持不变）。
   - 未同时改 state：校验 `issue.state_id ∈ 新类型可用集合`，不过 → 400 `issue_type_state_not_allowed`（带 `type_name/state_name`，产品方案 A4 拒绝式）。
   - 校验点在 `validate_state_transition` 之前（同位邻挂，保持「集合 → 流转」全局顺序）。
3. **新建**（`create`，请求显式含 `state_id/state` 且请求含 `type_id`）：校验 `requested_state ∈ requested_type 可用集合`，不过 → 400。未显式选 state 或未选 type → 不校验（产品方案 A6：落项目默认状态不拦）。

明确不挂：bulk 端点、intake、外部 API v1（同段 3 §7 口径；挂载点记录在此，供后续沿用）。
