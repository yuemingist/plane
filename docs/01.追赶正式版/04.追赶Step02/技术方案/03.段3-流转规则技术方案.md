## 1. 数据模型与迁移

### 1.1 模型选型：关系表 vs Workflow JSON 字段（产品方案 §4 评估）

| 方案                                     | 优点                                                                                                                                    | 缺点                                                                                                                              |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **A. 新表 `WorkflowTransition`**（选定） | FK 约束状态有效性；状态删除级联清理（DB 层保证，不用应用层扫 JSON）；行级唯一约束天然去重；与段 2「3 表」风格一致；历史 note 可引用行数 | 多一张表 + 一次迁移；前端矩阵保存需一次全量替换端点                                                                               |
| B. `Workflow` 加 `transitions` JSONField | 无新表；一次读写                                                                                                                        | 状态删除需应用层清理 JSON（软删除 State 下更易漏）；无法 DB 级防脏引用；查询/去重/审计弱；段 5 若按类型扩展会演化成大 JSON 难迁移 |

**结论：选 A**。理由：正确性约束（状态引用有效性）是本功能核心，DB 级保证优先于少一张表。

```python
class WorkflowTransition(ProjectBaseModel):
    workflow = models.ForeignKey(Workflow, on_delete=models.CASCADE, related_name="transitions")
    from_state = models.ForeignKey(State, on_delete=models.CASCADE, related_name="workflow_transitions_from")
    to_state = models.ForeignKey(State, on_delete=models.CASCADE, related_name="workflow_transitions_to")

    # unique_together (workflow, from_state, to_state)，含 deleted_at 条件约束（同段 1 partial unique 风格）
```

## 2. 后端端点

挂载在既有 `WorkflowViewSet`（`plane/app/views/workflow.py`），路由追加两条：

| 方法 | 路径                            | 语义                                                                                                                                           | 权限               |
| ---- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| GET  | `…/workflows/<pk>/transitions/` | 规则行列表（含 from/to 状态 id）                                                                                                               | ADMIN/MEMBER/GUEST |
| PUT  | `…/workflows/<pk>/transitions/` | **全量替换**规则：body `{"transitions": [{"from_state": id, "to_states": [ids…]}]}`（按源状态分组的产品形态在服务端展开成行）；空数组=清空规则 | ADMIN/MEMBER       |

PUT 语义细节：

- 服务端校验：from/to state 必须属于该项目、from ≠ to；非法 → 400 `{"error": "..."}`。
- 事务内 diff 后全删全插（规则行数 = 状态数 × 目标数，量级小，简单正确）；仅在规则集合实际变化时写一条 `WorkflowChangeLog(action="transition_rules_updated", note="N rules")`（不变更不写历史，避免噪音）。
- workflow 不存在/跨项目 → 404（沿用 `_get_scoped_instance`）。

### 2.1 流转校验挂载点（最小侵入）

新 helper：`plane/app/views/workflow.py` 内模块级函数（不新增文件）：

```python
def validate_state_transition(project_id, from_state_id, to_state_id) -> dict | None:
    """工作流启用且配置了 from_state 规则时，校验 to_state 是否允许。
    返回 None=放行；返回 dict=拒绝（含 error/code/from_state_name/to_state_name）。"""
```

- 查询路径：`Workflow.objects.get(project_id=…, is_active=True, deleted_at__isnull=True)` → `transitions.filter(from_state_id=…)`；无 workflow / 无该源状态规则行 → 放行（产品方案 A2）。
- 挂载：`plane/app/views/issue/base.py::IssueViewSet.partial_update`，在 `serializer.is_valid()` 之前——请求含 `state`（`state_id` 的 serializer 别名落点）且与 `issue.state_id` 不同时调用 helper；拒绝则直接 `Response(400)`，**不进 serializer.save、不触发 issue_activity**（既有留痕行为零改动：拒绝路径本就不会写活动）。
- 明确不挂：bulk 端点、intake、外部 API v1（产品方案 §7 记录，后续段沿用同一 helper）。

## 5. 风险与自查

- issue PATCH 是高频路径：helper 用两次轻量查询（workflow + transitions），仅当请求体含 state 时触发，无规则时零额外查询（一次 workflow lookup 命中即返回）。
- 不改既有活动留痕：拒绝发生在 serializer.save 之前，`issue_activity.delay` 不会被调用；放行路径行为不变。
- 对段 1/2 零回归：无规则 = 行为与今天一致；段 1 端点仅新增两条路由，不动既有签名。
